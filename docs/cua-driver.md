# Computer use in Pi: Cua Driver

Pi gets native desktop computer use through
[Cua Driver](https://github.com/trycua/cua) on the Mac, the Lenovo Legion Y720,
and the Raspberry Pi. WSL2 is excluded because it has no desktop session.

`packages/cua-driver.nix` pins upstream's checksummed `cua-driver-rs-v0.38.0`
release archives instead of the `curl | bash` installer. Its wrapper disables
upstream's self-update check (Nix owns the version) and its content-free
telemetry. `modules/home/cua-driver.nix`, imported by `modules/home/linux.nix`
and `modules/home/darwin.nix`, then:

- adds a `cua-driver` server to Pi's native MCP config
  (`~/.pi/agent/mcp.json`, generated by `modules/home/pi-mcp.nix`);
- installs upstream's agent skill for the same release as
  `~/.pi/agent/skills/cua-driver`;
- on Linux, runs `cua-driver serve` as a systemd user service bound to
  `graphical-session.target`. Pi's MCP server and the `cua-driver call` CLI
  share that one runtime through `~/.cache/cua-driver/cua-driver.sock` when
  pooling is disabled. With
  the agent-desktop option (below), the service operates a headless X11
  desktop instead of the graphical session.

The Lenovo enables a separate on-demand desktop pool. Its Pi MCP connections
lease their own desktop on first tool use. Shared legacy use remains available
explicitly through `CUA_LEGACY_DESKTOP=1`. See the concurrency section below.

The driver runs in upstream's default `standard` permission mode: observing,
clicking, and typing into any app is allowed without prompts. Treat it as
equivalent to giving the agent your keyboard and mouse.

## macOS

No Homebrew cask exists, and the driver only trusts its daemon and its
Accessibility/Screen Recording grants at `/Applications/CuaDriver.app`. The
macbook host's activation therefore copies the pinned, Developer ID-signed
bundle there (the same `ditto`, `codesign --verify`, and `lsregister` steps as
upstream's installer) whenever the installed version differs. `cua-driver mcp`
proxies to that app and starts it on demand.
The package wraps an immutable launcher so a clean build does not depend on
the app already existing in `/Applications`; runtime still executes that exact
installed bundle. `tests/cua-darwin-wrapper.nix` exercises this install branch
with a fixture on the current build host.

After the first `darwin-rebuild switch`, grant permissions once:

```sh
cua-driver permissions grant   # enable Accessibility and Screen Recording
cua-driver permissions status
```

The grants are bound to the signing identity and survive version updates.
The daemon is started by `open`, so the wrapper's telemetry setting does not
reach it; run `cua-driver telemetry disable` once if you want it off there too.

## Linux: the agent desktop

`services.cua-driver.agentDesktop.enable` moves Cua off Hyprland onto a
private X11 desktop: TigerVNC's Xvnc, Openbox and xcompmgr on `:47` at
1920x1080. The Raspberry Pi and Lenovo Legion Y720 enable it. The Pi also
sets `services.cua-driver.agentDesktop.headless = true`: both services start
with the lingering user manager at boot and survive graphical logout. The
Lenovo retains graphical-session startup. These options do not affect macOS.

Xvnc has no physical output. Its VNC endpoint is a 0600 Unix socket in the
0700 `$XDG_RUNTIME_DIR/cua-agent/` directory; neither VNC nor X11 listens on
TCP. A fresh, private MIT cookie is generated at each desktop start. A
private D-Bus session supplies AT-SPI, with `dbus-daemon` service activation
so the accessibility registry can start without a graphical login. This
isolates focus, pointer, clipboard and accessibility discovery from Hyprland;
it is not a security sandbox against processes running as the same user.

The desktop signals readiness only after authenticated X connections, the
window manager and the accessibility bus respond. The desktop supervises
Xvnc, the private session, Openbox and the compositor. Its service keeps the
driver running and restarts it when the desktop restarts.

Why X11: on the assessed Pi (Hyprland 0.56.1, Cua 0.38.0), app launch,
window discovery and capture worked, but background keyboard input returned
`background_unavailable` and foreground input returned
`production Hyprland input plugin is unavailable`. The terminal had no useful
AT-SPI controls. Hyprland 0.57 also has a known discovery parsing issue
([trycua/cua#6267](https://github.com/trycua/cua/issues/6267)). Native Wayland
keyboard input depends on a RemoteDesktop portal absent from Hyprland's
portal implementation. The isolated X11 desktop avoids these routes.

### Agent and human entrypoints

- `cua-agent-browser <url>` starts Chromium with X11, renderer accessibility
  and its own persistent profile in `~/.local/share/cua-driver/chromium`.
  The profile is created at runtime, never tracked. Keep browser sign-ins and
  credentials out of the repository.
- `cua-agent-editor <file>` opens Mousepad without reusing an existing instance.
- `cua-agent-run <command>` sets the X11 and private D-Bus environment for any
  other application. For Firefox, also pass `--new-instance --profile <dir>`.
- `cua-agent-view` opens a local VNC viewer for watching or taking over.
- `cua-agent-smoke` opens a disposable dialog and verifies window discovery,
  an accessible entry, semantic Unicode editing, foreground focus/shortcuts/
  typing, clipboard copy/paste, window movement, a PNG capture and the exact
  submitted value. It cleans up its own
  dialog and temporary artifacts, and exits nonzero on failure.

Pi, Claude and Codex discover both upstream's pinned skill and the local
`cua-agent-desktop` skill (Codex via `~/.agents/skills/`). CLI and Pi MCP
share the one daemon socket `~/.cache/cua-driver/cua-driver.sock`. Use
`delivery_mode:"foreground"` on this isolated desktop; background actions
remain limited by each application's accessibility support. Apps started
through `launch_app` inherit the daemon's environment. Single-instance
browsers and Electron apps still need isolated profiles.

### Concurrent desktop pool

`services.cua-driver.agentDesktop.pool.enable` adds the private lease broker
`cua-pool-manager` and a bounded set of on-demand desktop services. The Lenovo
declares four slots on displays `:48` through `:51`, an aggregate 8 GiB memory
limit and four CPUs of quota, with a 3 GiB memory limit per slot. The limits
include desktop processes and apps launched through pool commands; aggregate
swap is capped at 512 MiB. No slot
processes run until leased; the small broker is tied to the graphical session
(or the lingering manager on hosts using the headless option). Other hosts
retain the legacy desktop unless pooling is explicitly enabled.

Each lease gets its own X server, window manager, D-Bus/AT-SPI bus, Xauthority
cookie, clipboard, driver socket, browser profile and XDG directories. Sockets
include the lease identity and are never reused by a subsequent task. There is
no global lock on GUI actions or ordinary coding work. Allocation reserves one
slot briefly under a mutex and starts it outside that mutex, so slow startup
does not serialize other slots.

Wrap a GUI command or agent process to manage its lease automatically:

```sh
cua-pool exec --name browser-task --wait 60 -- cua-agent-browser-smoke --require-context-menu
```

Inside that command, normal `cua-driver`, `cua-agent-run`, browser and editor
commands route to the leased desktop. Each task belongs to its slot's systemd
slice, including app descendants. Closing or cancelling the command stops the
desktop and its apps. Explicitly wrapping a whole agent keeps its desktop for
the agent's lifetime; ordinary coding-only agents do not need this wrapper.
Unleased driver `call` commands require a lease or an explicit socket. Use
`CUA_LEGACY_DESKTOP=1` for intentional shared-desktop work on `:47`; the legacy
browser/editor/view helpers remain available. Both smoke commands automatically
lease a desktop when invoked without a lease, unless the legacy flag is set.

For GUI work spread across separate shell/tool calls, acquire explicitly:

```sh
cua-pool acquire --name research --wait 60
cua-pool call LEASE list_windows '{}'
cua-pool browser LEASE https://example.com
cua-pool run LEASE -- mousepad
cua-pool renew LEASE
cua-pool release LEASE
```

Replace `LEASE` with the `lease` value in the acquisition JSON and keep it for
the complete task. Browser and run commands stay attached to their process;
background them explicitly when a persistent app should outlive that shell
call. Returned task and download paths are private runtime data, never files
to commit. Release removes profiles and caches after stopping the slice while
preserving `work/` and `downloads/` under the task directory. Releasing twice is
safe. A failed stop quarantines the slot rather than giving live apps to a new
task. Pool exhaustion fails explicitly unless `--wait` supplies a bounded wait.

Manual leases expire after one hour without a call or renewal by default.
`exec` and active MCP proxies renew automatically. Automatically owned MCP
desktops are released after ten minutes without pending requests, controlled by
`services.cua-driver.agentDesktop.pool.mcpIdleSeconds`. Discovery and ping do
not reset that timer. Pending tools, including long-running ones, prevent idle
release. Use the MCP `pool_release_desktop` tool to release sooner; it refuses
while requests are pending. Neither policy releases a lease owned by a parent
`cua-pool exec` command.

A desktop failure, restart,
or broker restart invalidates the lease; old tokens cannot silently attach to
a replacement desktop. Runtime launchers also check the lease generation before
starting an app, refusing delayed jobs whose slot has been reassigned. Reacquire
and observe new state rather than replaying
old actions or handles. The broker stops all pool slices at shutdown and clears
orphaned runtimes at startup. Startup also removes disposable profiles, caches,
configuration and app data from abandoned task directories, preserving `work/`
and `downloads/`. All old slices must stop successfully before recovery cleanup
or new allocations proceed. Cleanup errors fail startup or quarantine a slot;
they are never silently ignored. These are GUI/cgroup boundaries, not a security
sandbox against other processes with the same Unix identity. Shared-file edits
and intentional human takeover still need coordination.

Pi's tracked MCP configuration uses `cua-pool mcp`. Initialization, tool-schema
discovery and ping require no desktop. The first tool call acquires one, then a
proxy forwards the pinned native MCP server's responses, including images, for
that connection. EOF, termination, idle expiry or `pool_release_desktop` releases
an automatically owned lease. The connection remains usable after release.
Following idle expiry or native-process loss, the first subsequent GUI call
reports that desktop state was lost without executing the action. Only a later
call acquires a fresh desktop; start with window discovery and never reuse old
window or session handles. Explicit release permits fresh acquisition on the
next GUI call. If the broker cannot confirm cleanup, the proxy reports that
failure and keeps the MCP connection available. A later GUI call reports lost
state before reacquisition; the broker still owns quarantine and restart
cleanup. CLI jobs also validate their lease and desktop invocation before
accepting a successful exit, so an external stop cannot silently count as task
completion. `end_session`
ends a native Cua session, not the connection's desktop lease. An MCP proxy
started inside `cua-pool exec` reuses that command's lease. Restart existing MCP
connections after activation to pick up this configuration. Do not combine an
unleased CLI with a pooled MCP connection and expect the same windows.

Use `cua-pool status` to see task names and occupied slots. From the human's
graphical terminal, `cua-pool view --slot 2` opens that slot's private VNC socket;
no VNC or X11 TCP listener is enabled. `cua-pool-smoke` acquires two free slots
and verifies concurrent input, distinct clipboard values, discovery isolation,
stale-token refusal and cleanup without touching other tasks.

### Validation and recovery

After activating the configuration:

```sh
systemctl --user status cua-agent-desktop cua-driver
cua-driver call health_report
cua-agent-smoke
cua-agent-browser-smoke
cua-pool-smoke # when pooling is enabled; needs two free slots
cua-agent-browser "file://$PWD/tests/cua-browser.html"
```

The browser fixture contains a form, select, checkbox, upload, download, drag
and drop, and a scroll target. Verify each visible result; successful input
acknowledgements alone do not prove delivery. Also test window resize,
right-click menus and any advertised recording tools.
Unsupported tools remain limitations rather than being marked passed.

`cua-agent-browser-smoke` automates the local fixture with a disposable Chromium
profile and download directory. It checks exact form results, Unicode, select
and checkbox input, uploaded filename, downloaded bytes, window geometry,
drag/drop, scrolling and repeated input after those actions. It inspects the
context popup separately from the main window and prints `LIMIT` when menu
items are unavailable; `--require-context-menu` makes that limitation a failure.
Use `--artifacts /path/outside/the/repository` to keep diagnostic screenshots,
states and the browser log on failure. They can contain file-chooser directory
names and must never be committed. The test cleans up its browser and profile.

The desktop supervisor keeps `NOTIFY_SOCKET` out of every child's environment:
both Xvnc and the private D-Bus daemon can announce readiness prematurely.
Only the supervisor signals readiness, after the window manager and AT-SPI
registry respond and the session publishes its bus address atomically. App
launchers also wait boundedly for a live private bus. The x86-64 flake check
`cua-readiness` exercises real X11/AT-SPI startup with a delayed session bus and
checks that a failed bus never announces readiness.

Repeat the smoke check after `systemctl --user restart cua-agent-desktop`,
after an unexpected X-server exit, while Hyprland is locked, and after a
reboot without graphical login. Reboot and logout tests are disruptive and
must be scheduled with the user. Stop the whole desktop with
`systemctl --user stop cua-agent-desktop`; stopping just the driver causes
the desktop service to start it again. Restarting the desktop closes its apps.

Targeted development builds avoid evaluating a full host:

```sh
nix build --impure --no-link --max-jobs 1 --cores 1 --expr \
  'let t = import ./tests/cua-desktop.nix; in [ t.desktop t.run t.smoke t.browserSmoke t.browser t.editor t.t3 ]'
```

On the Pi, full flake checks and host builds remain subject to the repository's
resource-safety rules. Use CI or a capable builder where possible.

### Raspberry Pi verification

The targeted ARM64 packages were built with one job and one core. Live tests
used temporary user services generated from the evaluated module, a separate
driver socket, and disposable data while the physical Hyprland session was
locked. The full Pi system build subsequently passed, the configuration was activated,
and the installed smoke check and service health checks passed.

| Capability | Verified result |
| --- | --- |
| Discovery, accessibility, semantic Unicode editing | Passed disposable dialog checks |
| Foreground keyboard and shortcuts | Passed entry readback and submitted-output checks |
| Isolated clipboard | Copy, clear and paste preserved the test value |
| Capture | Dialog PNG and visually inspected browser window |
| Window management | Dialog movement and Chromium move/resize readback |
| Pointer clicks and checkbox | Browser form returned the exact typed value and checked state |
| Drag and drop | Page reported `Dropped: CUA test item` |
| Scrolling | Previously offscreen marker moved inside the browser viewport |
| Context menus | Right-click created a discovered native popup |
| Upload/download | Native chooser selected the test file; downloaded contents matched |
| Service recovery | Killing Xvnc restarted the desktop and driver; full smoke check passed afterward |
| Trajectory recording | Nine turns with before/after PNGs and action JSON |
| Video recording | Finalized 1920x1080 H.264 MP4, 61 frames over 2.03 seconds |
| Headless Chrome runtime | No missing libraries; pinned shell rendered the local fixture |
| Installed T3 preview | Navigation, snapshot, Unicode typing, form/select/checkbox, upload/download, drag/drop and scroll passed after server restart |

GTK4 can publish incorrect element bounds. Cua refused foreground pointer
clicks on those controls; background semantic button actions worked. Use
fresh window screenshots when element geometry is unreliable. Accessibility
registration can also lag window mapping; the smoke check waits boundedly
for a usable entry. Another app or a keyring prompt can take focus, so run
the smoke check with a single controller and handle human-owned prompts
manually.

The persistent Chromium profile uses the browser's normal credential store;
its first start may ask the user to unlock the keyring on the private session.
Browser validation used a disposable profile with no credentials. Do not
weaken the persistent profile's password store to bypass that prompt.
Video recording uses the declared full FFmpeg build, since the default build
omits X11 capture. Recording stays off until explicitly requested. The short
video check does not establish sustained recording performance on the Pi.
Media acceleration, reboot/logout startup and sustained video throughput
remain untested. The installed T3 preview flow passed after its server restart.

### T3 preview browser

T3 preview is a separate headless browser, not a window on the Cua desktop.
The pinned T3 0.1.8 release downloads Chrome Headless Shell 157.0.8103.38 and
checks its archive size and SHA-256. `packages/t3-cli.nix` supplies its native
libraries through the CLI wrapper's `LD_LIBRARY_PATH`, including the same
environment for T3's `ldd` diagnostic. No imperative system package installation
is needed. A fresh machine needs network access for T3's verified browser
download on first use. Updates to T3 must revalidate this browser dependency
list and its pinned download behavior.

After activation, restart T3 outside an active agent task to pick up its new
wrapper, then verify a preview tab can navigate, snapshot, click, type,
upload, download and close. Browser credentials and cache remain runtime
state. Do not overwrite or stop an active T3 instance just to run a check.

Upstream labels the Linux arm64 Cua build a preview. Linux X11 does not imply
feature parity with macOS, nor does it make the user's Hyprland windows
controllable.

## Updating

Change `version` and the four hashes in `packages/cua-driver.nix`. Each
archive's SHA-256 is listed in the release's `SHA256SUMS` and asset digests;
convert it with `nix hash convert --hash-algo sha256 --to sri <hex>`.
Validate with `nix build --no-link .#cua-driver` on each architecture.
