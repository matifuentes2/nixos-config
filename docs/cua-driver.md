# Computer use in Pi: Cua Driver

Pi gets native desktop computer use through
[Cua Driver](https://github.com/trycua/cua) on the Mac, the Lenovo Legion Y720,
and the Raspberry Pi. WSL2 is excluded because it has no desktop session.

`packages/cua-driver.nix` pins upstream's checksummed `cua-driver-rs-v0.38.0`
release archives instead of the `curl | bash` installer. Its wrapper disables
upstream's self-update check (Nix owns the version) and its content-free
telemetry. `modules/home/cua-driver.nix`, imported by `modules/home/linux.nix`
and `modules/home/darwin.nix`, then:

- adds a `cua-driver` server to Pi's native MCP config
  (`~/.pi/agent/mcp.json`, generated by `modules/home/pi-mcp.nix`);
- installs upstream's agent skill for the same release as
  `~/.pi/agent/skills/cua-driver`;
- on Linux, runs `cua-driver serve` as a systemd user service bound to
  `graphical-session.target`. Pi's MCP server and the `cua-driver call` CLI
  share that one runtime through `~/.cache/cua-driver/cua-driver.sock`.

The driver runs in upstream's default `standard` permission mode: observing,
clicking, and typing into any app is allowed without prompts. Treat it as
equivalent to giving the agent your keyboard and mouse.

## macOS

No Homebrew cask exists, and the driver only trusts its daemon and its
Accessibility/Screen Recording grants at `/Applications/CuaDriver.app`. The
macbook host's activation therefore copies the pinned, Developer ID-signed
bundle there (the same `ditto`, `codesign --verify`, and `lsregister` steps as
upstream's installer) whenever the installed version differs. `cua-driver mcp`
proxies to that app and starts it on demand.

After the first `darwin-rebuild switch`, grant permissions once:

```sh
cua-driver permissions grant   # enable Accessibility and Screen Recording
cua-driver permissions status
```

The grants are bound to the signing identity and survive version updates.
The daemon is started by `open`, so the wrapper's telemetry setting does not
reach it; run `cua-driver telemetry disable` once if you want it off there too.

## Linux (Hyprland)

`modules/system/linux-desktop.nix` enables the AT-SPI accessibility bus.
The wrapper sets `CUA_DRIVER_RS_ENABLE_WAYLAND=1` so the driver uses its
Hyprland adapters, and puts `grim` on its `PATH` for desktop capture.
Upstream rates Hyprland support as experimental; the optional Hyprland
input plugin is not installed.

Known limitation with v0.38.0 on Hyprland 0.57: upstream cannot parse the
`specialWorkspace` entry that Hyprland 0.57 sends without an `id`
([trycua/cua#6267](https://github.com/trycua/cua/issues/6267)), so
`list_windows` returns no windows. Desktop screenshots (`get_desktop_state`)
still work; desktop-scope (screen-coordinate) input has not been verified
here. Bump the pinned version once a release contains the fix.

Verify after rebuilding (the AT-SPI change needs a fresh login):

```sh
systemctl --user status cua-driver
cua-driver doctor
cua-driver call list_windows   # uses the default socket shared with Pi
```

Upstream labels the Linux arm64 build (Raspberry Pi) a preview.

## Updating

Change `version` and the four hashes in `packages/cua-driver.nix`. Each
archive's SHA-256 is listed in the release's `SHA256SUMS` and asset digests;
convert it with `nix hash convert --hash-algo sha256 --to sri <hex>`.
Validate with `nix build --no-link .#cua-driver` on each architecture.
